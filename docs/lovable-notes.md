# Lovable-specific notes

What is tied to Lovable / Lovable Cloud and what to change when moving to a plain Supabase project and another build tool.

## Backend (Lovable Cloud = a managed Supabase project)
- Lovable Cloud is a Supabase project run by Lovable. There is no Supabase dashboard access and the service-role key and database password are not visible. To move: create your own Supabase project, apply `supabase/migrations`, and export data from Lovable (Cloud → Advanced settings → Export data).
- Auth: email/password, **email confirmation on**, no anonymous sign-ups, no Google. Configured through Lovable, not in the repo. Recreate in the new project: enable email provider, require confirmation, set Site URL and redirect URLs (the sign-up flow sends users back to the app origin).
- Email templates for auth use Supabase defaults (no custom templates configured).

## How migrations were applied
- Every change was applied by Lovable's migration tool, which wraps Drizzle Kit: it writes `drizzle/migrations/NNNN_name.sql` + `meta/_journal.json` and applies them to the Cloud database. `drizzle.config.ts` and the empty `drizzle/schema.ts` exist only for that tool — no Drizzle ORM is used.
- Each file was then copied byte-for-byte to `supabase/migrations/<timestamp>_name.sql`, which is the canonical set. `0014` and `0015` were copied during hand-over (`20260929150000`, `20260929160000`).
- Migrations were verified to replay cleanly on an empty Postgres 17 + a Supabase stub (`scripts/check-migrations.sh`). The rebuilt database matched the live one (same table and function counts).
- After leaving Lovable: delete `drizzle/`, `drizzle.config.ts`, and use `supabase migration new` / `supabase db push`.

## Set up outside the repo (until hand-over)
- **pg_cron job `business-date-rollover`** (`*/5 * * * *`, `select app.run_due_rollovers()`) was first created with a direct SQL call, not a migration. It is now recorded in `supabase/migrations/20260929170000_schedule_business_date_rollover.sql`. The new project must have the `pg_cron` extension enabled (Supabase: Database → Extensions).
- **Secrets**: `SUPABASE_URL`, `SUPABASE_PUBLISHABLE_KEY`, `SUPABASE_SERVICE_ROLE_KEY`, `LOVABLE_API_KEY` are injected by Lovable automatically. `RESEND_API_KEY` has **not** been added. Set these as environment variables on your host.
- The Resend connection was declined; `src/lib/outbox.server.ts` supports both a direct `RESEND_API_KEY` and Lovable's connector gateway (`LOVABLE_API_KEY`). Off Lovable, use `RESEND_API_KEY` only and remove the gateway branch.
- `.env` holds the `VITE_SUPABASE_*` values written by Lovable; it is regenerated by the platform. Replace with your own project's values.
- `supabase/config.toml` only contains the Lovable project id. Replace with `supabase init` output.

## Generated / platform files
- `src/integrations/supabase/client.ts`, `client.server.ts`, `auth-middleware.ts`, `auth-attacher.ts`, `types.ts`, `cron-auth.ts` were generated by Lovable. They are ordinary supabase-js code and keep working; regenerate `types.ts` with `supabase gen types typescript`. `cron-auth.ts` (`LOVABLE_CRON_SECRET`) is unused.
- `src/lib/lovable-error-reporting.ts` and `src/lib/error-capture.ts` send runtime errors to the Lovable preview. Safe to delete (remove their imports in `src/routes/__root.tsx` / `src/server.ts`).
- `AGENTS.md` and the `<!-- LOVABLE -->` block are instructions for Lovable's AI agent; the rules in it are still a good summary.

## Build tool and hosting
- TanStack Start v1 on Vite 7, configured through `@lovable.dev/vite-tanstack-config` in `vite.config.ts`. That preset builds with nitro targeting **Cloudflare Workers** and bundles Tailwind, path aliases and the TanStack plugin. To leave: replace it with `@tanstack/react-start/plugin/vite` + `@tailwindcss/vite` + `vite-tsconfig-paths` (and `@cloudflare/vite-plugin` if you stay on Workers, or a Node/Vercel/Netlify target).
- Server code (`*.functions.ts`, `*.server.ts`) must stay Worker-compatible if you keep Cloudflare.
- **No Supabase Edge Functions** were used. The brief asked for Edge Functions for staff invite, outbox and exports; they were built as TanStack server functions (`src/lib/invite.functions.ts`, `outbox.functions.ts`, `exports.functions.ts`) because this Lovable stack does not deploy Edge Functions. They could be ported to Edge Functions unchanged in logic.
- Publishing, preview URLs and the GitHub sync are Lovable features. The GitHub repo is a Lovable-created repo with two-way sync; do not force-push it while still on Lovable.
